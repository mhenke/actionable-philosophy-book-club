## Overall Impression

This is a codebase that *tries* to follow good design — the APOSD citations in comments, the deliberate IIFE encapsulation, the repository pattern over raw data — but tactical artifacts from refactoring have accumulated. The dead `renderHorizonCards()` call in the retry handler is the biggest concern: it's a runtime bug that will surface when the manifest fails to load. The three empty stub files are a close second — they add noise without value. Despite these issues, the core abstractions (`path.js`, `format.js`, `retry.js`, `fetchMarkdown`) are well-designed and genuinely reduce complexity.

---

## What's Working

1. **Deep caching abstraction** (`utils.js:21-42`): `fetchMarkdown` caches promises not values, preventing redundant network requests for identical files. LRU eviction with auto-cleanup on reject. Simple API, powerful behavior.

2. **Rigid security barriers** (`path.js:24-43`): `isSafePath` with two DOMAIN enums validates protocol, traversal, absolute paths, control chars, extensions, and roots. Used throughout the app — single source of truth for path safety.

3. **Defensive I/O everywhere** (`storage.js:43-104`): Every sessionStorage and localStorage operation is individually wrapped in try/catch with graceful fallback and error logging. No caller needs to handle storage failures.

4. **Robust async concurrency** (`reader-loader.js:191-225`): AbortController + generation counter pattern cancels stale requests, ignores out-of-order responses, and enforces 15s timeout. Clean pattern used well.

## Priority Issues

### [P0] Dead function call crashes retry flow
- **Principle**: Strategic Over Tactical (1), Modifying Existing Code (14)
- **Complexity symptom**: Unknown unknowns (runtime crash in error path)
- **Why it matters**: `dashboard.js:121` calls `renderHorizonCards()` which was removed when the 'horizon' status was deleted from `data-meeting.js:17`. When manifest load fails and user clicks retry, this throws `ReferenceError`. The error-recovery itself is broken — users stuck on a failed load get no retry path.
- **Fix**: Remove the call at `dashboard.js:121`. The horizon/draft consolidation already created `renderDraftCards()` — use that if draft re-render is needed.

### [P1] Three empty stub files in the build
- **Principle**: Better Together (7), Deep Modules (2)
- **Complexity symptom**: Cognitive load (files with zero logic that misdirect)
- **Why it matters**: `reader-hooks.js`, `reader-tree.js`, `reader-toc.js` (4 lines each) contain only a comment saying "Merged into reader-loader.js." They survive in the source tree and concatenation pipeline, adding download weight and misleading developers about where functionality lives. Classic shallow modules — interface cost exceeds implementation benefit.
- **Fix**: Delete the three files. Remove from the concatenation script that builds `dist/app.js`.

### [P1] Storage module mixes three unrelated concerns
- **Principle**: Different Layer, Different Abstraction (5), Information Hiding (3)
- **Complexity symptom**: Change amplification
- **Why it matters**: `storage.js:38-118` bundles video resume (sessionStorage), theme persistence (localStorage), and onboarding dismissal (localStorage). Three data domains, two storage mechanisms, different consumers — all in one module. Changing how video resume works risks affecting theme/onboarding code and vice versa.
- **Fix**: Split into focused modules: `storage-video.js` (resume position), `storage-preferences.js` (theme + onboarding), or keep storage.js as base key-building utilities and move feature-specific logic to consumer modules.

### [P1] Stale documentation references deleted status
- **Principle**: Modifying Existing Code (14), Comments Describe Non-Obvious (10)
- **Complexity symptom**: Cognitive load (misleading documentation)
- **Why it matters**: `data-repository.js:59` documents status param as `'One of 'done', 'upcoming', 'horizon', 'draft''` — but `data-meeting.js:17` only accepts `['done', 'upcoming', 'draft']`. `'horizon'` was removed from validation but the JSDoc survived. Misleads developers about valid inputs.
- **Fix**: Update `data-repository.js:59` to remove `'horizon'` from the status enum.

### [P2] Internal constants exposed as globals
- **Principle**: Information Hiding (3), Overexposure (17)
- **Complexity symptom**: Unknown unknowns
- **Why it matters**: `storage.js:129-130` exports `RESUME_MIN_SECONDS` (5) and `PROGRESS_SAVE_MS` (3000) to window. These are tuning constants used only within `storage.js:13-14`. Exposing them creates an implicit public API contract around private implementation details.
- **Fix**: Remove `window.RESUME_MIN_SECONDS` and `window.PROGRESS_SAVE_MS` exports. If tests need them, expose only under `window.__TEST__`.

### [P2] Vestigial __STORAGE_PREFIX configuration
- **Principle**: Nonobvious Code (13)
- **Complexity symptom**: Cognitive load (reader searches for definition that doesn't exist)
- **Why it matters**: `storage.js:12` and `theme-init.js:8` reference `window.__STORAGE_PREFIX || 'apbc:'`. But `__STORAGE_PREFIX` is never defined anywhere — no inline script, no module, nothing. The inline script `window.__STORAGE_PREFIX = 'apbc:'` in `index.html:20` is blocked by CSP (`script-src 'self'`). The fallback always wins. Reader wastes time searching for where prefix is overridden.
- **Fix**: Either (a) remove the `__STORAGE_PREFIX` mechanism entirely and inline `'apbc:'`, or (b) make the inline script CSP-compliant and remove the fallback.

### [P3] setup.js dumps 13 DOM refs to global scope
- **Principle**: Information Hiding (3)
- **Complexity symptom**: Change amplification
- **Why it matters**: `setup.js:25-36` assigns 13 DOM elements to `window.*`. Every module can couple to any DOM node by name. No encapsulation — renaming an element ID requires auditing every module that reads `window[dashboard|reader|etc]`.
- **Fix**: Mitigate with JSDoc annotations per export noting which modules consume it. Longer-term: introduce ES module pattern to control import boundaries.

### [P3] Nested IIFE in toast.js
- **Principle**: Consistency (15)
- **Complexity symptom**: Cognitive load
- **Why it matters**: `toast.js:41-56`: a second IIFE nested inside the module IIFE defines `ErrorHandler`. This unique pattern is used nowhere else in the codebase. A simple object assignment would work identically and be consistent with module conventions.
- **Fix**: Flatten the ErrorHandler definition — assign `window.ErrorHandler = { warn, error }` directly in the module IIFE body.
