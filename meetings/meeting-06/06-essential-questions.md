# Meeting 06: Essential questions

## Chapters 16 to 22: A Philosophy of Software Design

1. **Strategic repair vs tactical patch (Ch. 16).** Every change is a chance to improve the design, not just make the tests pass. Ousterhout pushes for leaving code in the shape it would have had if the new requirement had been known from the start, while many teams default to the smallest edit that works because it feels safer. When is a quick patch actually the right call, and how do you tell whether you did the best you could within your limits before you ship it?

2. **Consistency as leverage (Ch. 17).** When similar things are done in similar ways, readers can reuse what they already learned. That only holds if conventions are written down, checked automatically, and followed in each file through "When in Rome." The tension is that forcing different things to look the same also creates confusion, for example reusing a name for two different ideas or squeezing work into a pattern that does not fit. Where does consistency start to hurt, and when is it worth replacing a bad convention everywhere instead of living with it?

3. **Obviousness lives with the reader (Ch. 18).** Code is obvious when a first-time reader guesses right without stopping to work it out, not when the author feels it is clear. Ousterhout points to common ways this fails: a generic Pair that forces a reader to map getKey and getValue to real meanings, a variable declared as List but built as ArrayList, event-driven handlers that hide who calls whom, and a main that never exits because a constructor started background threads. Which of the three fixes fits each case: shrink what the reader must know, reuse what readers already know through better names and consistency, or put the missing fact right where the reader stands?

4. **Do modern trends help or hurt complexity (Ch. 19).** The chapter judges each trend only on whether it reduces complexity. Interface inheritance can deepen an abstraction by letting one interface serve many implementations. Implementation inheritance often leaks information between parent and child and makes the whole hierarchy harder to change. Agile and test-driven development, in this reading, push teams toward small feature increments and tactical fixes, while strong unit tests help by making larger refactors affordable. Patterns and getters and setters help only when they fit the case; more of them is not better. Which of these trends in our own stack most often adds complexity while looking helpful, and how would you spot it?

5. **Performance, critical paths, and deciding what matters (Ch. 20 to 21).** Ousterhout argues simple code is usually fast, and when it is not, the way to get faster is to design around the critical path: picture the smallest code that must run in the common case, then reshape the class so that path stays intact. The RAMCloud Buffer shows this concretely, collapsing three shallow layers into one method and a single availableAppendBytes test for three special cases, cutting about 410 lines and moving 8.8 ns to 4.75 ns. That is paired with a demand to measure before and after and with the frame from Chapter 21 to emphasize what matters through prominence, repetition, and centrality, and to hide what does not. When does a gain like that justify added complexity, and who on a small team gets to say what counts as matters?
